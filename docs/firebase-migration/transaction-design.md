# Stage B: transaction and consistency design

## Firestore transaction rules

Every transaction must read all documents that influence its writes before the
first write, use bounded document counts, and be safe to retry. Firestore
automatically retries contention; the service adds a finite retry/deadline and
maps exhaustion to a conflict response. No external network calls occur inside
a transaction. Immutable audit documents use deterministic IDs or an
idempotency record so a retried callback cannot duplicate history.

## Rental creation

Read in one transaction: customer, bike, `active_rental_locks/{bikeId}`, and
the request idempotency record if supplied/derivable.

Validate customer and bike are not archived, bike is `AVAILABLE`, and no
active lock exists. Write: rental document, active lock, bike status
`RENTED`, and charge `{rentalId}_1`. The initial charge period is start date
through start date + 6 days, due on start date, matching Java behavior.

The active lock is the Firestore equivalent of the SQL partial unique index.
Two concurrent requests contend on that lock; one commits, the other returns
the existing conflict. If the function retries, deterministic IDs prevent
duplicate rental/charge records. If the client retries without a stable
request identity, the server cannot prove two semantically identical requests
are the same; Stage C should add an optional idempotency mechanism without
requiring a new client field.

## Rental closure

Read: rental, its bike, active lock, and request idempotency record. Validate
active status and closure date not before start date. Write rental status
`CLOSED`, actual closed date, appended closure note, bike `AVAILABLE` only when
it is still `RENTED`, and delete the matching active lock.

The lock is deleted only if it points to this rental. A concurrent bike status
change or closure causes transaction retry/conflict rather than silently
overwriting another workflow. Existing future charges remain historical; no
unrequested cancellation is introduced.

## Recurring charge generation

Read rental and the deterministic next-sequence lock/current sequence document.
For `generate-next`, compute the next period from the highest sequence/current
cursor, reject cancelled rentals and dates beyond actual closure, then write
the charge and advance the cursor in one transaction.

For `generate-up-to-date`, do not issue an unbounded transaction. Repeatedly
run bounded `generate-next` transactions, each with a deterministic sequence
ID, until the target date or closure date is reached. A retry sees the
existing sequence and returns it rather than creating a duplicate. The
endpoint still returns the list of charges generated by this call.

## Payment recording

Read in one transaction: customer, optional rental, owner recorder, all
candidate unpaid/partially-paid charges in due-date order, and their current
allocation totals. Validate customer ownership, supported currency, positive
amount, allocation mode, and currency equality. Manual allocations must
belong to the customer, match currency, be positive, not exceed unpaid charge
balance, and have a sum no greater than the payment.

Write payment, allocation documents, updated charge status/paid totals, and
summary counters in the same transaction. FIFO processes oldest due charges
first. Because a large customer may exceed Firestore transaction limits, Stage C
must enforce a bounded candidate/allocation count and return a clear business
error rather than partially recording a payment. A payment must never be
created outside the transaction that creates its allocations.

Use a payment idempotency record when the request can carry a stable replay
identity. A retry after commit returns the original payment; a retry with a
different identity is a new payment by contract.

## Payment reversal

Read payment, all allocations, all affected charges, and the unique reversal
document. Verify payment is not already reversed. Recompute each charge's
remaining paid amount excluding the reversed payment, then write payment
status `REVERSED`, charge statuses, and one `payment_reversals/{paymentId}`
document atomically.

If a reversal retry sees the reversal document, return the existing reversed
payment or the existing business error matching the Java behavior. No
allocation history is deleted; the reversal is an audit event. Large payments
with too many allocations require a bounded rejection or a staged internal
workflow; never split a public reversal into visible partial success.

## Inventory movement

Read part and optional idempotency record. Validate active part. Convert the
positive request quantity to the signed delta exactly as Java does:
`STOCK_IN`/`RETURN` positive, `STOCK_OUT`/`SERVICE_USAGE` negative,
`ADJUSTMENT`/`REVERSAL` request-signed. Reject resulting quantity below zero.

Write the updated part quantity and immutable movement in one transaction.
Update `isLowStock` from the new quantity. The part read is the contention
point, so concurrent deductions serialize through transaction retries. A
duplicate movement key returns the original movement rather than deducting
stock twice.

## Service recording

Read bike, recorder, every referenced part, and an idempotency record before
writes. Validate bike is not archived, odometer is not lower than current,
parts are active and sufficiently stocked, and request currencies/quantities
are valid. Aggregate duplicate part IDs before checking and writing so a
request cannot pass two separate checks while exceeding total stock.

The Java implementation deducts parts for **every accepted service status**:
it validates and subtracts `partsUsed`, writes `SERVICE_USAGE` movements, and
creates part-usage rows without checking whether status is `PLANNED`,
`IN_PROGRESS`, `COMPLETED`, or `CANCELLED`. Firebase must reproduce that
behavior exactly; it must not add a completed-only deduction rule. The default
status is `COMPLETED`, but an explicitly supplied planned, in-progress, or
cancelled status still consumes the supplied parts. Status changes are not
exposed by the current API, so no later automatic refund is introduced.

Write service record, each service usage record, each negative
`SERVICE_USAGE` movement, updated part quantities/low-stock flags, and bike
odometer/next-service date in one bounded transaction. The service date and
default next-service date follow Java logic. A failed transaction writes
nothing. Do not call the general movement endpoint internally because that
would create nested transactions and could produce partial state.

## Read-only reports and list endpoints

Reads that do not mutate state use normal Firestore queries and summary
documents. A report is consistent at a snapshot/version boundary, not a
relational serializable transaction across the entire database. Each summary
document carries a version and last reconciliation time; staging tests compare
it with a direct calculation.

## Failure, retry, and limits

- Retry only Firestore contention/aborted errors.
- Do not retry validation, authentication, uniqueness, or business failures.
- Keep all transaction reads/writes below Firestore documented limits with
  explicit application caps.
- Return conflict/operational error after deadline; log request ID and
  transaction operation, not secrets or payment credentials.
- Reconciliation jobs detect orphan references, counter drift, duplicate
  idempotency keys, and ledger/quantity mismatches.

## Explicit transaction size limits

These are application limits, checked after validation and before any write.
They are deliberately below Firestore's 500-write transaction ceiling to leave
room for idempotency, counters, and lock documents. A request over a limit is
rejected as a business/validation error and records nothing.

| Operation | Maximum input items | Maximum transaction documents |
|---|---:|---:|
| FIFO payment allocation | 50 charges | 154 reads / 154 writes |
| Manual payment allocation | 50 allocation items | 154 reads / 154 writes |
| Payment reversal | 50 allocations/affected charges | 103 reads / 103 writes |
| Service part usage | 50 unique part IDs | 204 reads / 204 writes |
| Inventory movement | 1 movement | 4 reads / 6 writes |

The document budgets include the primary record, affected records, immutable
audit children, idempotency record, and summary updates. For example, the
50-item payment budget covers one payment, up to 50 charges, up to 50
allocation documents, optional idempotency, and bounded summary documents.
The service budget covers one service, 50 parts, 50 usage rows, 50 movement
rows, one bike, optional idempotency, and summary writes. A service request
with duplicate part IDs is aggregated before the 50-ID check. These limits
must be configuration constants and tested at their boundary values.

Payment recording, reversal, and service inventory operations are all-or-
nothing. There is no fallback to multiple public transactions and no partial
success response. If a request cannot fit, the client must retry with smaller
operations or an explicitly designed future workflow.
